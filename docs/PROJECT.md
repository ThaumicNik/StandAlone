# Project Context: Модуль устойчивой синхронизации данных

> Implementation status (13 November 2026): this document describes the broader
> thesis goals. Protocol v1 currently uses server-order whole-record replacement,
> without base-version conflict detection. The backend is Java/file-backed;
> Room/Ktor/PostgreSQL and additional platforms remain proposals. See PROGRESS.md
> for current implementation, VALIDATION.md for acceptance, and BENCHMARKS.md for
> the initial desktop measurements. A compiling app does not establish device
> behavior or complete the experimental research.

## 1. Общая информация

**Тип проекта:** выпускная квалификационная работа (бакалавриат), исследовательско-прикладной программный проект.

**Рабочая тема:** «Исследование и разработка программного модуля синхронизации данных мобильных информационных систем в условиях нестабильного сетевого соединения».

**Основной язык:** Kotlin.

**Целевая среда:** Kotlin/JVM с возможностью использования ядра в Android-приложениях.

**Основной результат:** переиспользуемая библиотека синхронизации данных, демонстрационное Android-приложение, серверная часть и результаты экспериментальных исследований.

Проект разрабатывается одним человеком в учебных целях. LLM-агенты выступают консультантами, архитекторами и ревьюерами. Основная реализация планируется вручную разработчиком, если явно не поставлена другая задача.

## 2. Суть проекта

Цель проекта — исследовать и разработать программный модуль, обеспечивающий надёжную синхронизацию данных между локальным хранилищем мобильного устройства и удалённой информационной системой при нестабильном сетевом соединении.

Модуль должен позволять приложению продолжать работу при временном отсутствии интернета, сохранять локальные изменения и передавать их удалённой системе после восстановления соединения.

При этом необходимо учитывать:

- Полное отсутствие сетевого соединения.
- Частые разрывы соединения.
- Высокие задержки передачи данных.
- Временную недоступность сервера.
- Потерю ответа сервера после успешного применения операции.
- Перезапуск приложения с накопленными изменениями.
- Одновременное изменение одних данных на нескольких сторонах.
- Повторную отправку операций и риск их дублирования.

Главная особенность проекта — **синхронизация должна быть реализована как самостоятельный программный модуль, а не как внутренняя логика конкретного Android-приложения**.

Модуль должен быть отделён от прикладной предметной области, конкретных UI-фреймворков и используемых технологий сетевого взаимодействия.

## 3. Общая архитектурная идея

Предполагается разделить систему на несколько независимых компонентов.

### 3.1. Источники данных

Источниками выступают локальные и удалённые информационные системы, участвующие в синхронизации.

Примеры:

- Локальная база данных SQLite / Room.
- Удалённый сервер с REST API, доступный через Retrofit.
- Другие источники, для которых можно реализовать совместимый адаптер.

Модуль не должен напрямую зависеть от Retrofit, Room или конкретной реализации базы данных.

Вместо этого источники подключаются через заранее определённые интерфейсы.

Не предполагается, что модуль сможет автоматически синхронизировать произвольную информационную систему без дополнительной интеграции.

### 3.2. Контракты взаимодействия

Необходимо разработать набор интерфейсов, определяющих взаимодействие между модулем и подключёнными источниками.

Контракты должны обеспечивать возможность:

- Получения данных из источника.
- Идентификации синхронизируемых записей.
- Регистрации изменений.
- Получения информации о версиях данных.
- Отправки изменений удалённой стороне.
- Обработки результатов применения операций.
- Обнаружения и обработки конфликтов.

Конкретная форма интерфейсов должна быть определена на этапе проектирования архитектуры.

При этом важно различать универсальную логику синхронизации и специфические возможности источников данных.

Например, поддержка атомарных транзакций или обнаружения изменений зависит от конкретного источника и не должна предполагаться автоматически.

### 3.3. Sync Core

Центральный компонент системы — независимое ядро синхронизации, реализованное на Kotlin.

Ядро отвечает за:

1. Управление жизненным циклом операций синхронизации.
2. Ведение журнала локальных изменений.
3. Управление очередью ожидающих отправки операций.
4. Повторную отправку после временных ошибок.
5. Отслеживание подтверждений удалённой системы.
6. Контроль версий синхронизируемых записей.
7. Обнаружение конфликтующих изменений.
8. Применение выбранных стратегий разрешения конфликтов.
9. Поддержание согласованного состояния данных после завершения синхронизации.
10. Предоставление приложению информации о текущем состоянии синхронизации.

Ядро не должно содержать пользовательский интерфейс, зависимости от Android SDK или бизнес-логику демонстрационного приложения.

### 3.4. Адаптеры и инфраструктура

Адаптеры реализуют контракты модуля для конкретных источников данных.

Инфраструктурная часть обеспечивает:

- Постоянное хранение журнала операций.
- Взаимодействие с локальной базой.
- Обмен данными с удалённым API.
- Планирование синхронизации.
- Реагирование на доступность сети.
- Выполнение фоновых операций в Android.

Предполагается использовать WorkManager для Android-специфичного фонового выполнения.

Необходимо обеспечить восстановление состояния синхронизации после завершения процесса приложения.

## 4. Основные механизмы

### 4.1. Offline-first

Прикладное приложение должно иметь возможность читать ранее загруженные данные и выполнять поддерживаемые операции без доступа к сети.

Локальные изменения должны сохраняться до попытки отправки на сервер.

Отсутствие соединения не должно приводить к потере уже сохранённых изменений.

### 4.2. Журнал изменений и очередь операций

Каждое зарегистрированное изменение представляется операцией синхронизации.

Предполагаемые сведения об операции:

- Уникальный идентификатор.
- Идентификатор изменённой записи.
- Тип изменения.
- Данные изменения.
- Исходная версия записи.
- Состояние выполнения.
- Дополнительная информация для диагностики и повторной отправки.

Очередь должна сохраняться в постоянном хранилище.

Необходимо исследовать и обеспечить согласованность между изменением локальных данных и регистрацией соответствующей операции.

Для источников с поддержкой транзакций предпочтительно атомарное сохранение данных и записи журнала.

### 4.3. Повторные попытки и идемпотентность

Временная ошибка соединения не должна приводить к безвозвратной потере операции.

Модуль должен поддерживать повторную отправку.

Каждая операция должна иметь устойчивый уникальный идентификатор.

Удалённая система должна поддерживать механизм защиты от повторного применения одной и той же операции.

Необходимо отдельно исследовать сценарий, когда сервер успешно применил изменение, но клиент не получил подтверждения.

Операция должна считаться завершённой только после получения достоверного подтверждения её результата.

### 4.4. Контроль версий

Записи должны иметь информацию о версии или эквивалентный маркер состояния.

При изменении данных модуль должен иметь возможность определить, соответствует ли исходная версия записи текущей версии удалённой стороны.

Если запись была изменена независимо, возникает потенциальный конфликт.

Предполагается использовать оптимистический контроль версий.

### 4.5. Разрешение конфликтов

Необходимо предусмотреть механизм обнаружения конфликтов и подключения различных стратегий их обработки.

Возможные стратегии:

- Автоматическое принятие удалённой версии.
- Автоматическое принятие локальной версии, если это допустимо.
- Объединение независимых изменений.
- Передача конфликта вызывающему приложению для ручного разрешения.

Конкретные правила разрешения конфликтов зависят от предметной области.

Модуль должен обеспечивать инфраструктуру обнаружения и обработки конфликтов, но не обязан самостоятельно понимать бизнес-смысл произвольных данных.

Неразрешённый конфликт не должен бесконтрольно перезаписываться или исчезать.

### 4.6. Согласование состояний

После восстановления связи и обработки накопленных операций система должна приводить локальные и удалённые данные к согласованному состоянию.

Необходимо предусмотреть не только отправку локальных изменений, но и получение изменений с удалённой стороны.

Конкретный протокол получения изменений, включая возможность использования версий, курсоров или полной сверки данных, определяется на этапе проектирования.

## 5. Демонстрационное Android-приложение

Для проверки работы модуля разрабатывается Android-приложение для выездных сотрудников.

Приложение является экспериментальным стендом, а не основным продуктом ВКР.

Предполагаемый функционал:

- Авторизация пользователя при доступной сети.
- Получение списка назначенных заявок.
- Просмотр подробной информации о заявке.
- Изменение статуса заявки.
- Добавление комментариев.
- Просмотр состояния синхронизации.
- Отображение ожидающих отправки изменений.
- Отображение ошибок и конфликтов.
- Продолжение работы с ранее полученными заявками без интернета.

Предполагаемые статусы заявки:

- Назначена.
- В работе.
- Приостановлена.
- Выполнена.

Приложение должно использовать API разработанного модуля, а не дублировать его логику внутри ViewModel или Repository.

Основная задача приложения — предоставить воспроизводимые пользовательские сценарии для демонстрации и измерения работы синхронизации.

Загрузка фотографий рассматривается как дополнительный функционал, который не должен задерживать реализацию основного механизма.

## 6. Серверная часть

Для экспериментов разрабатывается собственная серверная информационная система.

Предполагаемый стек:

- Kotlin.
- Ktor.
- PostgreSQL.

Сервер обеспечивает:

- Хранение синхронизируемых данных.
- Получение и применение операций клиента.
- Проверку уникальных идентификаторов операций.
- Контроль версий записей.
- Обнаружение конфликтующих изменений.
- Предоставление клиенту актуальных данных и изменений.
- Поддержку экспериментальных сценариев.

Серверная часть не должна ограничиваться обычными CRUD-операциями, если для выбранного протокола требуются специальные механизмы синхронизации.

Необходимо учитывать, что некоторые гарантии надёжности обеспечиваются совместной работой клиента и сервера.

## 8. Исследовательская часть

Проект должен содержать не только программную реализацию, но и экспериментальное исследование её характеристик.

Основная гипотеза: использование персистентной очереди операций, безопасной повторной отправки и контроля версий повышает надёжность согласования данных при нестабильной связи по сравнению с упрощёнными подходами.

Предполагается сравнить три варианта:

**Вариант A. Базовая синхронизация.**

Накопленные изменения отправляются после восстановления соединения без устойчивой очереди и контроля версий.

**Вариант B. Синхронизация с устойчивой очередью.**

Используется журнал операций, подтверждения и безопасная повторная отправка, но отсутствует проверка конфликтов по версиям записей.

**Вариант C. Полный механизм.**

Используется персистентная очередь, идемпотентность, контроль версий и обработка конфликтов.

Эксперименты должны проводиться на одинаковых исходных данных и последовательностях операций.

### Проверяемые сценарии

- Стабильное сетевое соединение.
- Медленное соединение.
- Полное отключение сети.
- Частые обрывы соединения.
- Недоступность сервера.
- Потеря подтверждения после успешного применения операции.
- Перезапуск приложения с непустой очередью.
- Конкурирующие изменения одной записи.
- Накопление нескольких операций над одной записью.

### Измеряемые показатели

- Количество потерянных изменений.
- Количество повторно применённых операций.
- Доля обнаруженных конфликтов.
- Количество незамеченных конфликтующих перезаписей.
- Время обработки накопленной очереди.
- Время доставки и подтверждения операций.
- Итоговая согласованность данных клиента и сервера.

Эксперименты должны быть воспроизводимыми. Для каждого сценария фиксируются исходные данные, параметры сети, последовательность действий, число повторов и критерии успешности.

Дополнительно необходимо проверить независимость ядра от конкретных источников данных посредством альтернативных реализаций адаптеров.

## 9. Границы проекта

Проект не предполагает:

- Разработку универсального фреймворка для любых информационных систем без адаптации.
- Автоматическое определение изменений в произвольных источниках данных.
- Поддержку всех существующих СУБД и сетевых протоколов.
- Реализацию полноценной распределённой базы данных.
- Автоматическое семантическое разрешение любых конфликтов.
- Разработку iOS-приложения.
- Создание промышленной системы мониторинга и администрирования.
- Реализацию сложной бизнес-логики управления выездными сотрудниками.

Приоритет — корректная архитектура модуля, гарантии сохранности операций, обработка конфликтов и экспериментальная проверка результата.

## 11. Инструкции для LLM-агентов

При работе над проектом необходимо соблюдать следующие принципы:

1. **Не смешивать ядро синхронизации и демонстрационное приложение.** Android-приложение является потребителем библиотеки.

2. **Не предполагать универсальность, которая не обеспечена контрактами.** Любой источник данных должен явно реализовывать необходимые возможности.

3. **Не считать предварительные архитектурные предположения окончательными решениями.** До реализации требуется обсуждать существенные компромиссы.

4. **Не усложнять проект без необходимости.** Это бакалаврская ВКР одного разработчика с ограниченным временем.

5. **Сохранять исследовательскую составляющую.** Архитектурные решения должны допускать тестирование, измерение и сравнение.

6. **Уделять особое внимание отказоустойчивости.** Следует анализировать сбои между сохранением данных, регистрацией операции, её отправкой, применением на сервере и получением подтверждения.

7. **Явно указывать гарантии и ограничения.** Например, не обещать exactly-once delivery при использовании сети с возможными повторными отправками. Необходимо различать доставку операции и однократность её применения.

8. **Не вводить преждевременно сложные распределённые механизмы.** CRDT, event sourcing, распределённые транзакции и подобные технологии допускаются только при наличии конкретной необходимости и обоснования.

9. **Предпочитать проверяемые архитектурные решения.** Ядро должно тестироваться независимо от Android, сети и реальной базы данных там, где это технически возможно.

10. **Не приступать к масштабной реализации без согласования архитектуры.** Сначала необходимо определить контракты, модель операций, гарантии, жизненный цикл синхронизации, протокол взаимодействия и границы ответственности.

## 12. Текущий статус проекта

Проект находится на стадии архитектурного планирования.

Общая концепция обсуждена с научным руководителем. Основное изменение относительно первоначального предложения — переход от механизма внутри конкретного приложения к самостоятельному переиспользуемому модулю синхронизации.

Пока не утверждены:

- Окончательная модульная архитектура.
- Формат контрактов источников данных.
