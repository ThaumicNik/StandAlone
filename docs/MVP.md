# Минимальная версия модуля синхронизации

Дата: 18.10.2026.

Статус на 03.11.2026: реализованы цикл синхронизации, постоянные JVM-хранилища, HTTP-адаптер, локальный REST-сервер и Android-демо. JVM-сценарии проверены; проверка Android на устройстве остаётся открытой. Подробности: [PROGRESS.md](PROGRESS.md).

## 1. Цель

Разработать независимую библиотеку, позволяющую читать и изменять локальные записи без сети, сохранять историю изменений и синхронизировать их с сервером после восстановления связи.

Этот документ уточняет минимальную версию концепции из `PROJECT.md`. Общие цели ВКР, включая сравнительные эксперименты и расширяемые стратегии конфликтов, сохраняются. Минимальная версия реализует только одну стратегию.

## 2. Публичные операции

| Операция | Назначение |
| --- | --- |
| GET | Получить текущее локальное состояние по идентификатору. Не требует сети и не создаёт запись аудита. |
| SET | Создать запись или полностью заменить её содержимое. Атомарно сохранить локальное изменение и операцию в журнале. |
| DEL | Пометить запись удалённой. Атомарно сохранить отметку удаления и операцию в журнале. |

Это операции библиотеки, а не обязательные названия HTTP-методов. Синхронизация запускается отдельно; успешный SET означает локальное сохранение, а не подтверждение сервера.

Для первой версии запись представляет собой идентификатор и непрозрачное для ядра содержимое. Точное представление содержимого выбирается при проектировании модели. Ядро не знает о заявках, статусах и комментариях, не объединяет отдельные поля. GET должен отличать отсутствие записи от ошибки хранилища.

## 3. Аудит и доставка

Каждое создание, изменение и удаление создаёт неизменяемую запись операции. Удаление предметной записи не удаляет аудит. Повторная отправка не создаёт новую операцию.

Минимальные сведения об операции:

| Поле | Смысл |
| --- | --- |
| operationId | Уникальный идентификатор, устойчивый при повторных отправках и перезапусках. |
| entityId | Идентификатор изменяемой записи, назначаемый без обращения к серверу. |
| clientId | Устойчивый идентификатор клиента. Не является средством авторизации. |
| localSequence | Порядок операций данного клиента, сохраняемый вместе с журналом. |
| type | SET или DEL. |
| payload | Полное новое содержимое для SET; отсутствует у DEL. |
| createdAt | Время создания для диагностики. Не определяет победителя. |

Состояние доставки хранится отдельно от неизменяемых сведений операции:

- PENDING: операция ожидает отправки или подтверждения.
- ACKNOWLEDGED: сервер подтвердил результат.
- REJECTED: сервер окончательно отклонил операцию, например из-за некорректных данных. Причина сохраняется и доступна приложению.

Временная сетевая ошибка оставляет операцию в PENDING. Число попыток и последняя ошибка являются изменяемыми диагностическими сведениями. Подтверждённые операции остаются в аудите.

В MVP не требуется постоянное состояние IN_FLIGHT: после сбоя процесса неподтверждённые операции можно повторить с теми же идентификаторами.

## 4. Правило порядка и конфликтов

Побеждает последняя уникальная операция, принятая сервером. SET и DEL участвуют в одном порядке. Сервер назначает возрастающую глобальную ревизию при первом успешном применении операции.

Глобальная ревизия задаёт порядок серверных изменений и используется как курсор загрузки. Ревизия конкретной записи равна ревизии последнего применённого к ней изменения.

При конкурирующих изменениях не выполняется автоматическое объединение полей. Итог определяется порядком принятия сервером. Это минимальная политика перезаписи, а не полноценный механизм обнаружения и измерения конфликтов. Проверка исходной версии и фиксация конфликтов для исследовательской части добавляются отдельно.

### Ограничения

- Часы клиента не используются для выбора победителя.
- Изменение, сделанное раньше, но отправленное позже, может перезаписать более позднее пользовательское изменение.
- Последующий SET восстанавливает удалённую запись. В том числе это может сделать давно накопленная офлайн-операция.
- Правило не гарантирует сохранение всех независимых изменений полей.

Очередь одного клиента отправляется последовательно в порядке localSequence. Пока результат операции неизвестен, следующая операция не отправляется. Это предотвращает перестановку SET и DEL одного клиента из-за повторных попыток. Цена упрощения: временная проблема одной операции задерживает очередь. После окончательного отклонения операция отмечается REJECTED, и очередь может продолжить работу.

## 5. Идемпотентность сервера

Сервер хранит operationId и результат применения. Повтор идентичной операции возвращает исходный результат без повторного изменения данных и без новой ревизии. Повтор того же идентификатора с другим содержимым является ошибкой протокола.

Проверка идентификатора, изменение записи, запись результата операции и запись изменения в серверный журнал выполняются атомарно. Конкурентные запросы не должны обходить защиту от повторов.

Гарантия: повторные попытки доставки с однократным применением в пределах сохранённой серверной истории идентификаторов. Гарантия доставки exactly-once не заявляется.

В MVP история идентификаторов и отметки удаления не очищаются. Правила безопасной очистки требуют отдельного протокола и пока исключены.

## 6. Удаления

DEL создаёт tombstone: идентификатор записи, признак удаления и ревизию. GET скрывает удалённую запись от обычного чтения, но инфраструктура синхронизации сохраняет отметку.

Удаление отсутствующей записи также допускается и фиксируется как операция. Оно должно распространяться на другие клиенты. После удаления разрешён новый SET с тем же entityId.

## 7. Локальное состояние и загрузка изменений

Необходимо различать подтверждённое серверное состояние и локальные неподтверждённые операции. Видимое состояние получается применением локальных ожидающих изменений поверх известного серверного состояния.

Загрузка старой серверной версии или подтверждение предыдущей операции не должны стирать более новый локальный SET или DEL. Окончательно отклонённая операция остаётся в аудите, исключается из ожидающих изменений, а приложение получает информацию об ошибке.

Для MVP достаточно одного последовательного цикла синхронизации на клиенте:

1. Загрузить серверные изменения после сохранённого курсора.
2. Применить их к подтверждённому состоянию, сохранив локальные ожидающие изменения.
3. Отправить накопленные операции по одной в порядке localSequence.
4. Сохранить подтверждения, не теряя локальные операции, созданные за время обмена.
5. Повторно загрузить серверные изменения после курсора.

Курсор продвигается только вместе с успешным сохранением полученных изменений. Ревизия ответа на отправку сама по себе не продвигает курсор: между двумя собственными операциями могли появиться изменения других клиентов.

На сервере порядок ревизий должен соответствовать порядку доступности зафиксированных изменений. Для небольшого стенда допустима сериализация применения операций в транзакциях; простой независимый счётчик без учёта порядка фиксации недостаточен.

Получение изменений допускает страницы с явным nextCursor. Отметки удаления входят в выдачу. При отсутствии новых операций и восстановленной связи клиенты должны в итоге получить одно серверное состояние.

## 8. Ответственность компонентов

| Компонент | Ответственность |
| --- | --- |
| sync-core | Модель операций, GET/SET/DEL, порядок обработки, цикл синхронизации, контракты хранилища и удалённой стороны. |
| Локальный адаптер | Транзакции, постоянное хранение записей, аудита, доставки и курсора. |
| Сетевой адаптер | Преобразование запросов и ответов REST в контракты ядра, классификация ошибок. |
| REST-сервер | Идемпотентное применение операций, ревизии, журнал изменений и удаления. |
| Android-приложение | Интерфейс, предметная логика, запуск фоновой работы и отображение состояния. |

Локальная транзакция является обязательной возможностью адаптера MVP. Нельзя обещать сохранность, если данные и журнал записываются независимо. Предметные изменения проходят через библиотеку; прямые изменения базы извне автоматически не обнаруживаются.

## 9. Кроссплатформенность и другие языки

Новое пожелание: заложить возможность использования ядра за пределами Android и Kotlin. Это расширяет первоначальную ориентацию PROJECT.md на Kotlin/JVM, но не означает готовую поддержку всех платформ.

Начальная конфигурация: Kotlin Multiplatform с одной JVM-целью, общая модель и алгоритмы в commonMain, общие тесты в commonTest. Первые потребители: Kotlin и Java. Другие платформы отложены; конкретные дополнительные цели будут выбраны по необходимости. Общая структура сохраняется, чтобы облегчить последующий перенос.

В общем коде избегать Android SDK, java.io, java.util и JVM-зависимых библиотек. Сетевой доступ, постоянное хранилище, генерация идентификаторов и получение времени должны использовать переносимые средства либо передаваемые зависимости.

| Потребитель | Возможный способ подключения | Граница обещаний |
| --- | --- | --- |
| Kotlin/Java на JVM | JVM-артефакт библиотеки | Для Java нужен удобный фасад, особенно для асинхронного API. |
| Android | Подключение совместимого JVM-артефакта или Android-цели | Совместимость проверяется отдельной сборкой приложения. |
| Swift/Objective-C | Kotlin/Native framework | Нужны отдельные сборка, экспорт API и проверка Apple-цели. |
| JavaScript/TypeScript | JS-цель и экспортируемый фасад | API и зависимости должны поддерживать JS. |
| Python/C# | Возможная нативная библиотека с C ABI и языковыми обёртками | Отдельный этап; прямого универсального подключения Kotlin API не предполагается. |

REST-протокол можно реализовать на любом языке. Это совместимость по сети, отличная от встраивания клиентской библиотеки: сама по себе она не переносит локальную очередь и офлайн-логику в Python или C#.

Наличие commonMain и успешная JVM-сборка ещё не доказывают кроссплатформенность. Для подтверждения потребуется сборка и запуск общих тестов хотя бы для второй цели. Экспорт публичного API проверяется отдельно для каждого заявленного языка.

Ни Flow, ни suspend-функции не считаются автоматически удобным межъязыковым интерфейсом. Фасады других языков проектируются после определения первого потребителя; сейчас не создаётся универсальная система обёрток.

- [Вызов Kotlin из Java](https://kotlinlang.org/docs/java-to-kotlin-interop.html).
- [Kotlin/Native](https://kotlinlang.org/docs/native-overview.html).

## 10. План реализации и проверки

Работа выполняется небольшими учебными шагами. Основной код пишет разработчик; помощник объясняет, проверяет текущие файлы и помогает с ошибками. Сервер и инфраструктурную заготовку можно поручать помощнику отдельной задачей.

1. Создать отдельный библиотечный Gradle-модуль sync-core. Разобрать разницу между модулем, package и публикуемым артефактом. Проверка: модуль виден Gradle и компилируется отдельно от приложения.
2. Описать тип операции и неизменяемую модель аудита. Проверить допустимость SET и DEL и отсутствие предметных зависимостей.
3. Определить транзакционный контракт локального хранилища. Сделать реализацию в памяти для проверки алгоритмов. Она не обеспечивает сохранность после перезапуска.
4. Реализовать локальные GET/SET/DEL и проверить создание, замену, удаление, восстановление и порядок операций.
5. Создать тестовую удалённую сторону и цикл синхронизации. Проверить повтор отправки после потери ответа и сохранение более новых локальных изменений.
6. Добавить постоянное хранилище. Проверить восстановление неподтверждённых операций и курсора новым экземпляром клиента.
7. Создать небольшой REST-сервер и сетевой адаптер. Зафиксировать формат запросов, ошибок, ревизий и страниц изменений до их реализации.
8. Подключить Android-приложение и проверить пользовательский сценарий без сети.
9. Подключить вторую выбранную платформу и при необходимости фасад второго языка.

Модульная сборка не равна публикации библиотеки: выкладка в Maven или другой реестр в первый шаг не входит.

## 11. Критерии готовности MVP

- GET, SET и DEL работают локально без сети.
- Все изменения имеют записи аудита; повтор отправки их не дублирует.
- После перезапуска сохраняются данные, неподтверждённые операции и курсор.
- Потеря ответа после успешного применения безопасно обрабатывается повтором той же операции.
- Порядок операций одного клиента сохраняется.
- Удаления передаются другим клиентам; SET может восстановить удалённую запись.
- Загрузка изменений и старое подтверждение не стирают новые локальные изменения.
- После прекращения записей и восстановления связи клиенты сходятся к серверному состоянию.
- Проверены конкурирующие SET и DEL двух клиентов с результатом по серверному порядку.
- Окончательно отклонённые операции видны в аудите и не повторяются бесконечно.

Дополнительные платформы отмечаются как поддержанные только после фактической проверки. Расширенные стратегии конфликтов, фотографии, сложная авторизация, очистка истории и оптимизация очереди в этот MVP не входят. Стенд используется локально с тестовыми данными.
